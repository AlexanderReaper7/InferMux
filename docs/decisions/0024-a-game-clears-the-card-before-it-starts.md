# 0024. A game clears the card before it starts, through a keyless control socket

- Date: 2026-10-12
- Status: accepted; built and tested 2026-10-12, running on strix by 2026-10-14 (the socket is `infermux:users` 0660 and answers the user without a key); no launch through `infermux-hold` watched yet
- Amended on 2026-10-17 (item 4): the launch always wins. The unload cuts the requests in flight on the GPU, interactive ones included, and is never refused, and `infermux-hold` starts the command whatever the daemon answers. Deployed on strix and the zbox at 18:22 and 18:30 CEST.
- Amended on 2026-10-17 (item 5): while `infermux-hold` runs, no model starts on the GPU, for any client. The aide's choice, after dikt loaded its speech model beside Warframe a second after the unload.
- Amends [0004](0004-infermux-request-priority.md): an unload by hand cuts an interactive request on the GPU, and a hold refuses its start there (the rule). Amends [0017](0017-a-priority-process-takes-the-card.md): during a yield an interactive request still loads its model, except under a hold.

## Context

On 2026-10-12 Warframe ran at 2-5 fps on strix: in-game GPU time 496-539 ms, the card 100% busy at 174 W of 340 W with 4% memory-controller use. The cause was in the journal and EE.log:

- 19:45:20, InferMux loaded Qwopus3.6-35B on the 3080 for Episteme.
- About 19:50:20, Warframe started. At t=3.1 s it read its VRAM budget: `Local: Budget = 267714560`, 255 MB of 10 GB. Between t=3.7 and t=5.6 s it created every render target, then logged `Only 239MB / 10GB video memory free` and set texture streaming to `MINIMIZED (Budget: 0B)`.
- 19:50:26, the warden measured Warframe at 28% and paused; 19:50:27 the 35B unloaded.

The game never recreates its render targets (no `ResizeBuffers` after t=3.1 s), so what it placed outside VRAM stayed there for the whole run. Relaunched at 20:23 with 7.4 GB free and nothing else changed (same gamescope launch options, fullscreen and focused), it read a 7.36 GB budget and ran at 97 fps with 9.39 ms of GPU time.

The warden cannot see this coming. It polls every 5 s and counts load only at 25%, and a game reads its budget before it creates any. `priority_processes` (0017) does not help either: it matches NVML's compute list, and a Proton game is in the graphics list only. Anything that waits for the game to appear on the card is too late.

## Decision

The user, 2026-10-12, each asked in turn.

1. **The game's launch clears the card first.** `infermux-hold -- <command>` sets a manual pause, unloads the models, waits until InferMux holds no VRAM, then runs the command. When the command exits it sets `auto`. As a Steam launch option: `infermux-hold -- gamescope ... -- %command%`. Rejected: noticing the game by process name, which is still after the budget is read.
2. **A command of InferMux's, not a script in nixcfg.** It ships and is tested with the API it calls.
3. **No key.** The daemon also listens on a Unix socket, `-control-socket`, mode 0660 and owned by `-control-group`, that answers only `/warden/verdict`, `/warden/resources` and the controls (`/warden/manual`, `unload`, `forgive`, `cancel-batch`, `comfyui/free`), without a key. File permissions are the authorization. Rejected: exempting loopback, because `tailscale serve` forwards tailnet requests to the daemon from 127.0.0.1, so any tailnet device could have paused the warden and unloaded models. Also rejected: a key file for the command.
4. **The launch always wins.** The user, 2026-10-17: `infermux-hold` is never refused and never waits, for any client. The requests in flight on the GPU are cut, each client gets an error it can retry, and ComfyUI gets `/interrupt`, a queue clear and a stop (0030). Replaced: from 2026-10-12 the unload was refused while an interactive request was in flight (0004), tried every second for 30 s, and a card still not clear refused the launch.

   How it is done (the agent's choices):

   - `/warden/unload` is never refused, for the user's click as for `infermux-hold`. It cuts every request in flight on the GPU, interactive and batch. A cut request whose answer has not started gets 503 with `{"error":{"type":"gpu_held",...}}` and `resume_quiet_seconds` (300) as `Retry-After`. llama-swap's access log and InferMux's request stats record that 503, the status the client got (the coordinating session's call of 2026-10-17; until then the log read 499 and the stats 200). A model with another place fails over to it at once, as on any 503. The 300 s keeps a client that obeys the header from loading the model again while the game reads its budget, and it is what a batch request gets during a pause. An answer already streaming is broken off. A job is paused and held for the same 300 s (0023). A session is closed with 1013, moving data or not (0018, 7).
   - The CPU's models stop too, unless an interactive request is in flight on the CPU. They hold no VRAM, so 0004 still keeps them.
   - `infermux-hold` pauses, unloads once and reads `/warden/resources` every 250 ms for up to `-timeout` (10 s) until InferMux holds no VRAM. That wait is for the driver to free the stopped servers' memory, never for a client. A refused pause (a disabled warden answers 409), a failed unload, or a card still not clear at the timeout is a warning on stderr and in `notify-send`, and the command starts.
5. **Nothing starts on the GPU while the command runs.** The aide's choice of 2026-10-17, under item 4's rule that `infermux-hold` always wins. At 21:47:21 CEST that day `infermux-hold` paused the warden on strix and unloaded `qwen3-asr-1.7b` for Warframe. At 21:47:22 dikt's warm-up, a `GET /upstream/qwen3-asr-1.7b/health` sent at a key press, started it again. dikt's key is unmarked, so its requests are interactive, and an interactive request loaded its model during a pause (0017, 3). Warframe and the speech server then filled 9.5 of the card's 10 GiB, and the HDMI monitor got no framebuffer (nvidia-drm: `Failed to allocate NvKmsKapiMemory for dumb object of size 33177600`).

   How it is done:

   - `infermux-hold` opens `POST /warden/hold` on the control socket before it pauses and unloads, and keeps that request open until its command has exited. The daemon counts a hold for each open request. The keyed listener on :5001 has no such route.
   - While a hold is open, the start gate (0025, 0028) refuses every start of a model on the GPU, whatever asked for it: a request of any class on any route, a GET to `/upstream/`, ComfyUI's `/comfyui/` (0030), and the preload of a server a config reload makes. The answer is 503 `{"error":{"type":"gpu_held",...}}` with `resume_quiet_seconds` (300) as `Retry-After`, the answer of a request the unload cut (item 4). A model with another place fails over to it at once. The CPU device's models still start.
   - The hold lives as long as the connection. An `infermux-hold` that dies, by SIGKILL too, closes it, and the hold ends. A daemon that restarts has no holds, and `infermux-hold` dials again every 250 ms until the socket is back. Holds stack: two games hold the card until the last one exits. Rejected (the aide's choice): a hold kept in a file or in the daemon's state, which a crash could leave in place, the way a manual pause can stay (0001).

   How it is built (the agent's choice): the count and the route are in `internal/warden/hold.go`, and `Warden.Fits` refuses with `HeldError` before it takes the GPU's start slot (0029), and again once the card has been read, freeing the slot, so a hold that begins during a start still stops it. The client is `hold.Client.Hold`.

How it is built (the agent's choice): `Warden.LocalControl` is the keyless handler. `serveControl` in `infermux_control.go` binds the socket. The client is `internal/hold`, and the command is `cmd/infermux-hold`. The module's `services.infermux.controlGroup` turns on both and puts `infermux-hold` on the PATH. "Clear" means `/warden/unload` answered 200 and `/warden/resources` shows `our_vram_mb` at 0. A daemon that is not running (no socket, or connection refused) holds no models, since they are its children, so the command starts with a warning. The warden cancels a request's context with a cause that carries the 503 (`yielded`, which has the methods of llama-swap's `swaputil.HTTPError`). llama-swap takes a cancelled context for a client that hung up and marks it 499, so `swaputil.MarkClientClosed` calls `answerCut` (`internal/swaputil/infermux.go`) first, a marked hook in upstream's `http.go`, and writes that cause through llama-swap's own writers. The warden writes the refusal itself only where llama-swap did not.

## Consequences

- The by-hand unload skips `interactive_recent_seconds` and cuts what is in flight on the GPU. A reply the user is reading as it streams stops mid-sentence, and the next request loads the model again. Launching a game, or pressing Unload all, is the user's own statement that the card is wanted.
- `/warden/unload` stops every model, the CPU device's too (0022), although those hold no VRAM, except while an interactive request is in flight there.
- A card InferMux could not clear launches the game anyway, with the 2 fps run of 2026-10-12 as the risk. The unload no longer waits for anything, so what is left is a server that takes over 10 s to exit, or another program's VRAM, which InferMux does not hold and cannot free.
- A manual pause ends once the warden's own verdict changes (README). With the game's load at or above 25%, the warden pauses on its own and keeps the card until 300 s after the game exits. A game below 25% keeps the manual pause until `infermux-hold` exits. If `infermux-hold` is killed with SIGKILL before the game creates load, the pause stays until the next verdict change or a hand `auto`. That is the 0001 residual risk in a new form, not mitigated here. The hold ends with the process (item 5), so only the consumers' pause stays.
- No model starts on the GPU while `infermux-hold` runs, the user's own included (item 5). A dictation or a chat during a game gets 503 `gpu_held` at once, or goes to the model's other place when it has one. dikt sends its warm-up once per key press, logs the 503 as a failed warm-up and does not retry it; the transcription at key release gets the same 503. Outside a hold, an interactive request during a yield by load or by a priority process still loads its model (0017, 3).
- A consumer told `resume` during a hold, once the warden's own verdict has changed, gets 503 `gpu_held` for each request to a model on the GPU, since the unload left none running.
- A daemon that restarts during a hold, as a deploy does, has none until `infermux-hold` dials again, within 250 ms of the socket's return. llama-swap's preload runs before the socket opens, so a preloaded model would start in that window. Neither host preloads a model.
- If the user had set a manual pause before the launch, `infermux-hold` leaves it in place at exit.
- Two games under `infermux-hold` at once: the first to exit sets `auto` under the second, and the hold stays until the second exits (item 5). Only the consumers' pause, for a game below 25% load, ends early.
- The daemon joins `controlGroup` to hand it the socket. On strix that group is `users`, so the user's existing session can open the socket without logging in again.
- Handing the socket to the group is an `fchownat`, which the unit's `~@privileged` filter forbids. The first deploy on strix, 2026-10-12, was killed with SIGSYS at start. The user chose to allow `@chown` when `controlGroup` is set, over a systemd socket unit (no chown and no group for the daemon, but a connection to a stopped InferMux would start it). A dynamic user can only chown its own files to groups it is in.
